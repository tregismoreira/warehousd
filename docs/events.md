# Events

An inventory of every state transition the broker and its adapters actually produce today, a taxonomy of which of them are candidates for push delivery, and a recommendation on transports and an event bus. Written to close P2-1 parts B and C and P2-3 from Cortex's change requests — see `.context/attachments/LKnXTj/warehousd-change-requests.md` — and to record what Phases 1 through 3 of the plan that answers them did and did not add to this inventory.

This is an analysis document. Nothing here ships a webhook endpoint, an SSE route, or an outbox table — see §6 for why, and the roadmap for what is planned instead.

## 1. The state transitions that exist today

Derived from reading the code named below, not from the README or from Cortex's own hypothesis list. Where a source emits nothing durable, that is stated rather than left implicit.

**Content lifecycle** — `writeChangeLog` (`packages/broker/src/verbs/history.ts`) appends one row to `app.change_log` per document write: collection, document id, revision id, `op` (`create`/`update`/`delete`), `status` (`pending`/`approved`/`rejected`), actor, timestamp. Called from three places: `proposeDataset` (`verbs/propose.ts`, status `pending`), the direct-write path (`verbs/mutate.ts`, status `approved`, not itself in the plan's source table but the third caller of the same function), and `applyApproval`/`applyRejection` (`verbs/propose.ts`, status `approved`/`rejected`). `importCollection` (`import/run.ts`) also calls it, once per imported row, after its own transaction commits. This is already a durable, cursor-readable feed — `GET /v1/changes?since=<seq>` — and it is the substrate every content-lifecycle candidate event below rides on.

**Proposal lifecycle** — `packages/broker/src/verbs/propose.ts`. `proposeDataset` parks a write as a pending revision. `decideProposals` (Phase 1) commits or rolls back a whole list of approve/reject decisions in one transaction; `approveProposal` and `rejectProposal` are one-item batches through the same driver. Every decision writes one `app.change_log` row (above) and one `app.audit_events` row (below); a batch of N decisions shares one `batch_id` (migration 0013) across N audit rows.

**Governance** — `packages/broker/src/grants/manage.ts`: `requestGrant`, `approveGrant`, `denyGrant`, `revokeGrant` each mutate one row in `app.grants`. `narrowerThanInherited` computes a warning returned inline in the same API response as an approval — nothing is stored or pushed. `grants/eval.ts` (`loadActiveGrant`, `loadActiveGrants`) treats expiry as a property of the query: a grant with `expires_at < now()` simply fails to match, and nothing fires at the instant it lapses. `expiringGrants` and `accessReview` are both pull queries the manager inbox runs on demand, not transitions that emit anything.

**Membership** — `packages/broker/src/workspaces/members.ts`. `setMember` inserts or updates a `(workspace, user)` role row and does not distinguish "added" from "role changed" — both go through the same upsert. `removeMember` deletes one, and refuses (via a thrown `LastAdminRemoval`, not an event) rather than leave a workspace with no admin.

**Per-document policy** — `packages/broker/src/acl/manage.ts`. `setDocumentAcl` replaces a document's ACL principal list, including clearing it to make the document public again within its grant. `setUserGroups` replaces one source's (`sso` or `manual`) group memberships for one user.

**Ingestion** — `packages/broker/src/indexing/ingest.ts`: `ingestFile` returns `status: "indexed"` (content stored, chunked, and — if an embedder was supplied — embedded in the same pass) or `status: "skipped"` (the extracted text's checksum matched what was already stored; the Phase 0 regression target). It throws `DocumentRejected` for a corrupt file, a missing required taxonomy term, or a value that will not coerce. `indexing/upload.ts` (`uploadFile`, `planUpload`) is the resumable-upload wrapper around the same function; `planUpload` answers which files a collection already holds byte-for-byte, from the database, never from anything the client remembers. `indexing/index.ts` is a pure barrel re-export — it defines no behavior and emits nothing beyond what `ingest.ts` and `upload.ts` already account for. `embedding/sync.ts` (`embedCollection`, `embedChunks`) writes vectors into the documents table; `onProgress` is an in-memory callback for the caller's own render loop, not a durable event — nothing is written to `app.change_log` or `app.audit_events` when a run finishes.

**Import** — `packages/broker/src/import/run.ts`: `importCollection` is the single write path into `data_live`. It writes one `app.audit_events` row for the whole file (op `import:<mode>`, column names and row counts, never a cell value) through `makeAuditWriter`, plus one `app.change_log` row per imported document row, written after the data transaction commits (the import role holds no privileges in `app`, so it cannot write its own feed entry inside its own transaction). `import/report.ts` is pure formatting — it turns an `ImportErrorSummary` into the headline and grouped lines both the CLI and the console render, computes no new fact, and emits nothing of its own.

**Schema** — `packages/broker/src/apply/apply.ts`. `applyConfig`/`applyOn` diff the running config against the database and apply DDL; `resolveDestructiveChanges` refuses (via a thrown `Error`, not an event) a change that would drop or strand a populated `data_live` table. Neither writes an audit row or a change-feed entry. The only trace either leaves is `app.collections.updated_at` changing and the operator's own CLI/boot log — this is an operator-time, pre-authentication surface, not a broker decision.

**Access** — `packages/broker/src/credentials/keys.ts` (`createClientSecret`, `revokeClientSecret`, `rotateClientSecret`) and `credentials/platform-keys.ts` (`createPlatformKey`, `revokePlatformKey`) mutate `app.client_secrets`/`app.platform_keys` rows directly and write no audit row themselves — auditing is left to the caller, and the only in-scope caller that does it is the platform API (see Platform, below). `oauth/client-policies.ts` (`setAllowedScopes`) records a promotion only as `promoted_at`/`promoted_by` columns on `app.client_policies` itself; its own comment on `setCanManageAcl` states plainly that auditing is the caller's job, not enforced in this file. `apps/web/lib/lockout.ts` records a failed local sign-in in `app.login_attempts` — a table that exists solely to drive the lockout counter, decayed after the attempt window and deleted on the next success, and **not** joined into `app.audit_events` or exposed to any admin console. `POST /v1/token` (client_credentials and token-exchange) writes no audit row and no change-feed entry at all.

**Platform** — `apps/web/app/v1/platform/**`. `workspaces/route.ts` (`workspace_created`), `workspaces/[id]/route.ts` (`workspace_deleted`), `workspaces/[id]/clients/route.ts` (`platform_client_created`), `workspaces/[id]/members/route.ts` (`member_set`, `member_removed`), `workspaces/[id]/seed/route.ts` (`workspace_seeded`) each call `platformAuditWriter` and write one `app.audit_events` row under that op name. There is no suspend operation anywhere in this surface or elsewhere in the broker.

**Every decision** — `packages/broker/src/audit/decision.ts`. `makeAuditWriter(app, ctx, enabled, destination, batchId?).allow()`/`.refuse()` is the one call every broker verb ends in, refusals included (non-negotiable 3). This is the highest-volume and highest-risk source in the inventory: every row named above that carries an audit trail at all goes through it, and it is also the only place several transitions above are recorded at all (grant decisions, ACL edits, platform actions).

## 2. The taxonomy table

One table per area above, in the same order, so every §1 source maps onto at least one row below or carries an explicit "not present" or "emits nothing" line in §1 itself. Volume and inference risk are qualitative — this deployment has no production traffic to measure against — and push-eligibility answers "should this ever reach a push channel", not "is a push channel built" (none is; see §6).

## 3. Deliberate exclusions, with reasoning

These must never reach a push channel, regardless of how the delivery mechanism is scoped:

- **`grant.denied`** — a stream of "this request was declined" events tells anyone who can see it which collections exist and who wanted access to them, which is exactly the inference "denied means absent" (non-negotiable 4) exists to prevent. Reachable instead via the `app.grants` row itself, whose `status`, `decided_by` and `decided_at` already carry the decision — the console's own grants views and `GET /v1/grants` (`apps/web/app/api/grants/route.ts`) surface it there, scoped to the caller, with no separate audit trail involved.
- **`query.refused`** (the generic `decision.refused` row above, for every read/mutation refusal reason) — the same reasoning at higher volume: a caller watching a refusal stream learns which collections and documents exist, and which of them a given identity reached for, without ever holding a grant on any of them. Reachable instead via a grant-checked query over `app.audit_events`, or via `audit.sink: webhook` for an operator's own SIEM.
- **`document.not_found`** — the specific refusal reason within the above that most directly names a document. A document excluded by a grant's filter or an ACL returns the identical `not_found` a document that does not exist at all returns (`verbs/propose.ts`'s `resolveBase`, `verbs/history.ts`'s `listRevisions`, `verbs/read.ts`'s `getDocument`), which is the whole point — the two must be indistinguishable to the caller. Broadcasting the reason on a push channel would make them distinguishable to a subscriber with wider standing than the caller who was refused, and would confirm existence to the caller they were refused. Reachable instead via a grant-checked query over `app.audit_events`.
- **`auth.failed`** — a stream of failed sign-ins is a target list for whoever is credential-stuffing the account it names. Unlike the three above, this one carries an extra wrinkle: it is **not** reachable via a grant-checked query over `app.audit_events` today, because `apps/web/lib/lockout.ts` records it only in `app.login_attempts`, a table that exists purely to drive the lockout counter and is exposed to no admin console. That gap is worth fixing on its own terms — see §7 — but it does not change the answer here: still excluded from push, and the "reachable elsewhere" half of this document's own rule does not currently hold for this one event.

## 4. The identifiers-only rule, per transport

Every transport that ever pushes a content-lifecycle or proposal-lifecycle event from §2 carries exactly `{ event, collection, documentId, workspaceId, timestamp }` and nothing else — no field name, no field value, no query result. A webhook fires before its recipient is grant-checked at the moment of delivery; content in the payload would bypass the whole permission model, because the only enforcement a payload can carry is enforcement that already ran before the event was queued, which cannot account for a grant that changes between then and delivery. This is stated once, here, and §5 references it per transport rather than restating it — every transport listed below is bound by it without exception.

## 5. Transports, with a recommended order

**1. Change feed polling** — what exists today. `GET /v1/changes?since=<seq>` (`packages/broker/src/verbs/history.ts`) is cursor-based, indexed, and correct under concurrency: it holds back any row an in-flight transaction could still be sitting on, using `pg_snapshot_xmin` as the watermark, rather than a fixed delay that would be both laggy and still wrong for a long-lived transaction. What it does not do: no long-poll, so review-UI latency has a floor at the poll interval, and an idle workspace still pays one indexed query per poll regardless of whether anything changed. It already carries only identifiers (§4) — nothing about pushing this feed changes its payload shape.

**2. SSE over the change feed** — recommended ahead of webhooks for Cortex's stated need. The consumer already holds an authenticated session for a live review UI, so it can be grant-checked continuously for the lifetime of the connection rather than once at subscribe time the way a webhook subscription is. It is the same identifiers-only payload as polling (§4), delivered as the underlying `app.change_log` rows are written rather than on a fixed interval — the mechanism changes, not the event set. `proposal.batch_decided` (§2) is the strongest case for this: a review UI's "did my page publish" question is answered by one push instead of a poll cycle away.

**3. HTTP webhook** — for server-to-server consumers with no session to hold open. Needs delivery-state tracking (has this event reached this subscriber), retry with backoff, and per-subscription grant scoping — a subscriber must only receive events for collections and documents it could read, or delivery becomes a side channel around the grant system, the same leak as a content-bearing payload one level up. Bound by §4 like every other transport. Not built in this phase; see §6 for the substrate it would feed from if it ever is.

**4. Slack / email** — for human-facing governance events, especially `grant.requested` and `grant.expiring_soon`. `docs/roadmap.md` already names "Grant expiry notifications" as blocked on exactly this: an outbound channel the deployment does not have. Same identifiers-only rule (§4) applies to the notification's structured payload; the message text a human reads can name the collection and the requester, both of which the recipient (an approver) is already entitled to see.

**5. Message bus** — see §6.

The order above is a recommendation, not a build queue: nothing in this phase implements any of them. It answers "if one of these gets built, in what order does it pay for itself" — SSE first because it needs no new delivery-state machinery and directly answers the review-UI latency question; webhooks next because they are the first transport that needs one; Slack/email after, because the product gap it closes is narrower (governance notifications, not general reactivity); a message bus last, and only after §6's questions are answered.

## 6. Event bus: the verdict

**Reject option 4 (embed a Kafka producer).** This would put a hard broker dependency and delivery semantics inside the core library, contradicting the pure-library positioning `eslint.config.js` enforces with `no-restricted-imports` — no HTTP, no MCP, no UI, no LLM imports in `packages/broker`. That rule has a sibling that this document is making explicit for the first time: no message broker dependency in the core either, for the same reason. This is the one option that breaches it outright, and there is no proportionate gain named anywhere in the change requests that would justify doing so.

**Recommend option 2 (document a CDC recipe, build nothing).** A deployment is BYO Postgres, so the operator already owns the database — Postgres logical replication plus Debezium produces a Kafka stream with zero code in this repository. Stated plainly, what that recipe actually yields: raw collection rows with no grant semantics at all. Acceptable for a landing zone the operator already trusts with the whole database — a warehouse ingest running under the same trust boundary as the Postgres instance itself — and unacceptable for anything a grant is supposed to govern, because logical replication reads the table, not the view the broker enforces through. An operator who wants this can already build it today without warehousd's involvement; documenting the recipe (which extensions, which publication, which caveats) is the only thing worth doing here, and it costs nothing to maintain because it is not code.

**Record option 3 (transactional outbox plus a pluggable relay) as the shape if anything is ever built.** An outbox table in the same schema as the write it accompanies, written in the same transaction — one row per event, `{ id, event, collection, document_id, workspace_id, batch_id, created_at, delivered_at }`, no field values, matching §4. A separate relay process polls or logically-replicates the outbox and ships to whatever sink is configured, so the core stays provider-agnostic: the broker writes rows, and knows nothing about Kafka, SQS, or a webhook target. The webhook transport in §5 would read from the same outbox rather than being a second write path, which is what keeps "an event was recorded" and "an event was delivered" from drifting into two different answers about the same decision. **This table is not created in this phase** — it is recorded here as the shape a future PR would take, not as work done.

**The SIEM case is already solved**, separately from all of the above. `audit.sink: webhook` (`packages/broker/src/audit/sinks/webhook.ts`) ships every decision to a collector synchronously, with the downgrade rule intact — an allow whose delivery to the collector fails becomes a refusal, the same as an allow whose Postgres insert fails. Nothing about an event bus improves on this for audit forwarding; it already carries the highest-volume, highest-risk source in this inventory (`decision.allowed`/`decision.refused`) to an operator-controlled destination with the one property a bus cannot offer here — synchronous, all-or-nothing delivery.

**Is identifiers-only streaming useful enough to justify any of this?** For CDC: no, on its own — a pipeline that receives only document ids has to fetch content back under its own identity for every id it saw, which is a query per event, and at that point the pipeline could have driven the change feed directly instead of standing up a message bus in front of it. It becomes useful only when paired with option 2's raw-table CDC, which trades identifiers-only for no grant semantics at all — there is no middle position where a bus carries both content and enforcement. For SIEM: yes, but that case does not need identifiers-only, because `audit.sink: webhook` already ships the full audit row (still never a field value — see the intent-recording rules in `audit/decision.ts`) to a destination the operator configured and trusts, which is a stronger answer than a bus topic any consumer with access can read. **The finding: identifiers-only streaming is not worth building as new infrastructure.** It duplicates the change feed for application consumers (§5 already covers that need better, with grant-checking intact) and it under-serves the CDC/analytics case, which wants content and can get it more honestly through option 2's documented recipe, at the cost that recipe is explicit about.

**The positioning cost, stated plainly.** Option 4 breaches "no message broker dependency in the core" directly, is rejected above, and would need real justification — none exists in the requests. Option 3 does not breach it: the outbox is a Postgres table the broker already knows how to write to, and the relay that turns outbox rows into bus messages is a separate process this repository would ship as an optional adapter, not a dependency of `packages/broker` itself, the same way `audit.sink: webhook` reaches Kafka's cousins (HTTP collectors) today without `packages/broker` importing an HTTP client. Option 2 does not touch the broker's dependency surface at all — it is documentation, run entirely outside this repository's process boundary. The trade, argued rather than elided: warehousd's value proposition is that access is governed at query time against a caller identity, and every message-bus option except "do nothing" and "document a recipe with no grant semantics" would need to either re-implement that enforcement outside the broker (a second copy of the drift hazard `sql/build.ts` already warns about for a second filter language) or ship content ungoverned. Neither is worth what it costs.

## 7. Findings for Cortex

- **P2-2 is closed and needs no work.** Re-indexing or re-uploading unchanged content already generates zero embedding calls (`ingest.ts:202`'s checksum gate, now pinned by `packages/broker/test/embed-gating.test.ts`), and cross-workspace vector reuse is deliberately not built — the `prev` lookup in `ingestFile` is scoped by `workspace_id`, so two workspaces holding the same document each embed their own copy. That is the safe answer, not a gap: a shared vector row would create a new place derived content comes to rest, which the request itself says not to add while hard-purge stays deferred (§8).
- **Field projection already exists.** `fields` on `POST /query` and `GET /search` (`QueryIntent.fields`, enforced through `resolveGranted` in `verbs/guard.ts`) lets a caller ask for exactly `id`, `order`, `text` and skip the embedding column and the rest of a row's metadata. No new surface was needed for this.
- **A denied field refuses `field_denied` (403) and does not silently vanish — this is deliberate, not a bug to fix.** A field that does not exist refuses `unknown_field` (404). The split exists so a typo is distinguishable from a denial; collapsing the two into one silent-absence behavior, as the original request assumed, would make every misspelled field name look identical to a posture the caller was never going to be told about. If a consumer needs a denied field to be silently absent from the response rather than refused, the fix on the caller's side is to omit that field from `fields` rather than request it and expect a quiet drop.
- **Keyset pagination landed on `POST /query` as `after`/`nextCursor`, not as a `GET` with a `filter=` string DSL**, because the alternative is a second filter language that would have to agree with `FilterSchema` forever — the exact drift hazard `sql/build.ts` documents and `test/filter-parity.test.ts` exists to police. One filter language, validated once in the broker, is worth the small ergonomic cost of a POST body over a query string.
- **The change feed is already a correct, cursor-based tail — measure its real polling cost before asking for push.** `GET /v1/changes` is indexed, holds no window under concurrent writes (§5), and its only real cost is one indexed query per poll against an idle workspace. Before building any of §5's later transports, the honest next step is measuring that cost against the actual poll interval and workspace count a deployment runs, not assuming it is a problem.
- **`auth.failed` has no grant-checked reachability today, unlike the other three excluded events (§3).** `apps/web/lib/lockout.ts` records a failed sign-in only into `app.login_attempts`, a table that exists purely to drive the lockout counter — it never reaches `app.audit_events`, and no admin console reads it. Closing that gap (writing an audit row alongside the lockout counter, then exposing it through the same grant-checked path the other three use) is separate work from this phase and is not proposed here; this is a finding, not a fix in flight.

## 8. Future purge surfaces

Per the standing instruction in the change requests: hard-purge is deferred by decision, and nothing that lands before it should make it harder to add — concretely, nothing should introduce a new place content or derived vectors come to rest. None of Phases 1 through 3 does, and the reason differs by phase:

- **The batch decision path (Phase 1) writes the same revision rows the single-decision path already wrote.** `decideProposals` calls the same `applyApproval`/`applyRejection` functions `approveProposal`/`rejectProposal` always called, in a loop inside one transaction — it adds a `batch_id` column on the audit row (migration 0013) and nothing on the content side. A batch of N proposals leaves exactly the N revision rows N individual approvals would have left.
- **The cursor (Phase 2) is stateless and stored nowhere.** `encodeCursor`/`decodeCursor` (`packages/broker/src/sql/cursor.ts`) round-trip a `{ v, f, d, k }` tuple through base64url with no server-side state — there is no cursor table, no session tying a cursor to a caller, nothing a purge would ever need to find and remove.
- **The batch read (Phase 3) stores nothing.** `queryBatch` runs each labelled sub-query through the unchanged `query()` path and returns results keyed by label; it holds no cache, writes no new table, and its only durable trace is the audit rows every sub-query and the envelope already write under the existing rules.
